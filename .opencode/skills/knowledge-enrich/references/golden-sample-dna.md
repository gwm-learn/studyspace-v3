# 文风基准拆解：netfilter 框架入门

基准文件：`20-平台与系统/21-Linux/06-网络子系统/01-netfilter/netfilter框架入门.md`

改任何一篇之前，先花五分钟重读它的 §1–§4，抓"手法"而不是"章节"。下面把它拆成可复用的八条。

## 1. 标题下面先给承诺

> 一个包的一生经过哪五条链、每条链上能挂哪几张表、两个世界怎么并行、同一条链上谁先动手。通用教材，不含任何具体问题单的内容。

一句话说清**读者读完能回答哪四个问题**，再补一句"不含什么"。这比"本文介绍 netfilter"有用得多。

**照做**：一句话结论下面，紧接着写"本篇定位：覆盖 X，不覆盖 Y（去 Z 看）"。

## 2. 三句话模型 + 一个类比

> 只记三句话：**链**＝在哪儿拦（位置），**表**＝拦下来干什么（用途），**规则**＝具体拦谁、怎么处理。

三个概念各给一个"＝"定义，然后立刻用类比落地（检查站 / 排队 / 裁决）。类比要短，且**说清它在哪里失效**。

**照做**：任何有 3 个以上核心概念的笔记，§1 都用"三句话 + 一句类比"开场。类比后面加一句"类比失效的地方是…"。

## 3. 先合并、再拆开

它先给一张"三条路径叠在一起"的总览图，再给"三条泳道分开"的拆解图，并明说读法：

> 先看合并图，再看拆开图：上图把三条路径叠在同一张拓扑上——共用 PREROUTING 与 POSTROUTING，只在中间分岔。

**手法**：复杂流程 = 一张总览（找共性）+ 一张拆解（看差异），两张图回答不同问题。不要指望一张图干两件事。

## 4. 表格让读者"不用背"

它的链表有六列：`链 | 什么时候被问到 | 这时已知什么 | 能挂的表 | 典型用途 | 容易踩的坑`，并直接点出推理关系：

> 同一个包只走其中一条路，所以每条链「这时能看到什么信息」不同，能挂的表也就不同。看第三列就能推出第四列——不用背。

**手法**：把表格设计成"已知 → 可做"的因果链，而不是并列清单。最后一列永远放边界/误判。

**照做**：每张表至少问一次"读者能不能从左边推出右边"。能推，就说明结构对了。

## 5. blockquote 的三级用法

它用引用块承载三类"正文之外"的信息，节奏非常稳定：

| 类型 | 例子 | 作用 |
|---|---|---|
| 推论 | "**由此得到一条实用推论：**一个报文要么被 bridge 转发、要么被 IP 路由转发，**不会两者都走**。" | 把机制推成可操作结论 |
| 边界 | "**一个边界：**三层转发的出口如果恰好是桥的成员口…路径与桥转发不同，别混。" | 防止读者过度外推 |
| 别过度断言 | "**一处别过度断言：**…是否真被调用，取决于桥的发送路径与 `br_netfilter` 是否加载。" | 保留不确定性，不装作全知 |

**照做**：一篇里三种都要有。只有推论没有边界 = 结论过强；只有边界没有推论 = 读完不知道能干什么。

## 6. 编号走查 + "答错的后果"

它把排查写成三步，而且每步都写清"答错会怎样"：

| 步骤 | 问什么 | 怎么答 | 答错的后果 |
|---|---|---|---|
| ① 判泳道 | 这包是给我的、过路的、还是我发的？ | 抓包看目的地址 | 泳道判错，后面看哪条链都是白看 |
| ② 找世界与链 | 它在哪个世界被问 | 二层转发 → 桥的 FORWARD | 拿 iptables 拦桥转发，永远不命中 |
| ③ 看表与规则 | 那条链上站着谁 | `-L -v` 看计数 | 规则在但没命中，会被误判成"没生效" |

**手法**：顺序本身就是知识。"答错的后果"这一列，比步骤本身更能防止误判。

**照做**：凡"选型 / 排查 / 决策"类内容，都给①②③并写后果列。

## 7. 同构对照，省一半篇幅

二层那一章不重新讲一遍，而是明说"和 1.1 那张表完全同构，对着看一遍，就知道同名不同族差在哪"。

**手法**：当两个对象结构相似时，先讲透一个，再用"只换三样"的方式讲第二个。读者只需记差异。

**照做**：适用场合如 IPv4/IPv6、有线/无线、Linux/厂商实现。差异点用"只换 N 样"开头。

## 8. 前后呼应，把散点收成一句

> 上一章那句「表按 raw→mangle→nat→filter 固定顺序执行」，其实就是这张图在三层世界的表现。

它会在后面章节回指前面的结论，把"规则、图、表"三处线索拧成一股。这是"读起来像教材"和"读起来像手册"的分水岭。

**照做**：每个大节结尾，用一句话回指前面的模型；每个新模型出现时，说明它和旧模型的关系。

## 语气特征（可直接模仿）

- 短句、判断句。删掉"可能 / 大概 / 一般来说 / 众所周知"。
- 第二人称"你"直接对读者说话，但结论用第三人称陈述。
- 加粗只给**一句结论**，不给整段；一段里最多两处。
- 破折号用于补充限定，不用来转折情绪。
- 反问句只用于引出"为什么"（"为什么内核里这个协议族叫 `PF_BRIDGE`、不叫 `PF_L2`？"），一节最多一次。

## 不要学的地方

基准文件不是每处都该抄：

1. **章节名**：它有 `## 5 · 新人最常踩的八个坑`、`## 7 · 常用命令速查`、以及抓包相关内容。**本仓库禁止这三类章节**（见 `AGENTS.md`）。要学的是它的"边界列 + 推论块"，不是这些标题。
2. **转档残留**：开头"原文生成时间"、结尾"本 Markdown 由原 HTML 转换而来""本报告不含…"这类话，是新笔记不需要的。新笔记结尾只用"本篇定位 / 素材来源 / 待验证"三行。
3. **`#sN` 锚点**：它用 `- [1 地基](#s1)`，而 GitHub 实际锚点是 `#1--地基`，点了不跳。跟随所在目录的既有惯例即可（本仓库多数笔记用 `#sN`），不要单独发明第三种写法；除非用户要求统一修锚点。
4. **篇幅**：它不短也不长，是"按需写"的结果，不是标准。**主题小就写短**，硬凑长度就是注水；反过来，加深时也不必向它的体量看齐，该长就长（见 `enrich-workflow.md` §4）。

## 一句话检验

改完之后，用这三个问题自检：

1. 只读 §1，能不能复述整篇的模型？
2. 随便挑一张表，最后一列是不是"边界/误判"？
3. 每个 `##` 里，有没有至少一句"因为…所以…"？

三个都"是"，文风就到位了；有一个"否"，回去补那一节，别继续往下写。
