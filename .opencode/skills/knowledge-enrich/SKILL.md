# Knowledge Note Enrichment

Use this skill when a note **already exists** and the user wants it **deeper, better structured, or rewritten in a stronger style** — not created from scratch.

Typical triggers:

- "这篇太浅了，按 netfilter 那篇的样子重写"
- "继续丰富这篇，把原理讲透"
- "把结论补成流程，加图"
- "这篇只有提纲，扩成能看懂的文章"
- "上一轮重构的笔记，做第二遍"

**Not this skill:** 目录里还没有这篇、要从素材建第一篇 → 用 `knowledge-refactor`。两者共用同一套模板、图流程和审计脚本，差别是本技能**只改已有文件，不新建同主题笔记**。

## Non-negotiables

1. **保真优先**：原文的事实、代码块、链接、图引用不能丢。删改必须能说出理由（错误 / 重复 / 越界）。
2. **一次一篇**：先诊断、再动笔、再自检。不要边读边改、不要同时开三篇。
3. **文风基准唯一**：`20-平台与系统/21-Linux/06-网络子系统/01-netfilter/netfilter框架入门.md`。学它的**解释手法**，不抄它的章节名（本仓库禁止 `抓包`/`常见坑`/`命令速查` 三类章节，见 `references/golden-sample-dna.md` §4）。
4. **slug 稳定**：不改文件名、不改已有标题编号、不破坏 `#sN` 目录锚点；改标题就要同步 TOC。
5. **不重复造篇**：内容变多但仍属同一主题，就写进同一篇；确实跨了两个主题，才拆篇（拆篇走 `knowledge-refactor` 并更新索引）。
6. **图只增不重**：优先复用已有图；新增图接着目录编号往下排，插在对应章节并配"读图"。
7. **术语表只增不减**：除非原条目本身是错的。
8. **深度靠解释，不靠长度**：禁止用同义反复、背景铺陈、AI 腔排比把篇幅撑大。
9. **不自动 commit/push**，除非用户明确要求。

## Workflow

### 0. Load context and measure baseline

- Read：目标笔记、同目录 `.readme.md`、`images/.readme.md`、文风基准（一次即可，不必通读全文，读 §1–§4 足够抓手法）。
- 记录基线（只用于报告"变了多少"，不是目标值），后面报告要用：

  ```bash
  wc -l -c <note>.md
  grep -c '^## ' <note>.md        # 章节数
  grep -c '!\[' <note>.md         # 图数
  ```

- 跑一次审计，拿到客观缺口：

  ```bash
  python3 .opencode/skills/knowledge-refactor/scripts/audit_kb.py <dir> --figure-gaps
  ```

### 1. Diagnose（先打分，不动笔）

按 `../knowledge-refactor/references/quality-checklist.md` 的 10 条逐项打 0/1，再补一遍"深度症状"扫描：

| 症状 | 长什么样 | 对应动作 |
|---|---|---|
| 只有结论没有原因 | "X 用于 Y" 后面就没了 | 补"为什么需要 / 不用会怎样" |
| 结构是功能清单 | 按"模块 A/模块 B"罗列 | 改成"问题 → 机制 → 边界" |
| 表格没有边界列 | 只有"字段 / 作用" | 加"坑 / 边界 / 误判"列 |
| 只有成功路径 | 一段顺流程 | 加异常分支表 |
| 状态机缺失 | 该有却一句带过 | 补状态图 + 定时器表，或明写"没有" |
| 图位置错 | 全堆在开头 | 移到对应章节，补"读图" |
| 图不够 | 多段流程共用一张 | 一段流程一张 |
| 术语表不合格 | 只有中文、缩写无全称 | 三列重排，补英文全称 |
| 二手断言未核 | "据说/一般都" | 核对或标"待验证" |
| 与相邻笔记重复 | 同一段在别处也有 | 留一处正本，其余改链接 |
| 提纲腔 | 每条一行、无连接词 | 合并成有主语的段落 |

输出一张**差距表**（项 / 现状 / 目标 / 动作），这就是本次的施工图。用户在场时，把它当作"动手前的确认点"。

### 2. Plan the rewrite

写一张**章节映射表**，逐节说明去留：

| 原章节 | 处理 | 理由 |
|---|---|---|
| `## 3 · 关键字段` | 保留 + 加边界列 | 信息对，缺"坑" |
| `## 5 · 状态机` | 重写 | 原文只有一句 |
| （无） | 新增 `## 先分清三个概念` | 读者最容易在这里混 |
| `## 7 · 参考` | 合并进新 §8 | 避免两个参考节 |

同时定三件事：

- **篇幅不限**：不设行数、字数或 KB 上限。复杂主题（多协议、多平台、多条失败路径）写到几千行也合理；简单主题写短同样合理。唯一判据是"删掉任一段会不会丢信息"，不是体量。初建时的体量参考是防止"先铺开再补"，对加深不适用。
- **保留清单**：原文里必须原样留下的代码块、命令、链接、图引用（改完要逐条核）。
- **拆分判断**：材料够写两篇时先停下来问用户，不要自顾自拆。

### 3. Rewrite section by section

按 `../knowledge-refactor/references/note-template.md` 的骨架重排，用 `references/enrich-workflow.md` 的"加深手段库"逐节施工。顺序建议：

1. 先写 §1 一句话模型（这节定生死：一句话说不清，就是还没想清）。
2. 再写"为什么"章节（为什么需要、不用会怎样、为什么这样设计）。
3. 然后是结构/字段/报文（表格必须有边界列）。
4. 最后写流程与异常（这里最需要图）。

写作时的硬要求：

- **每节至少一个"为什么"**：不是"是什么"的复述。
- **每个表格至少一列限制条件**：作用 + 边界成对出现。
- **每个结论给一个反例或失效条件**：只说"能"不说"什么时候不能"的段落一律补。
- **推论用 blockquote**：`> **推论**：…`、`> **边界**：…`、`> **待验证**：…`（这是基准笔记的标志性手法）。
- **短句、判断句**：删掉"可能/大概/一般来说/众所周知"。
- **保留原有链接与命令**：改写不是重打，是重排 + 补写。

### 4. Figures

Follow `../knowledge-refactor/references/figure-workflow.md`。

- **先按 `.图表模板/figure-style.md` §2.1 选图型**：分层→`stack`、交互→`sequence`、依赖/分叉→`graph`、分流→`decision`、演化→`timeline`、线性步骤→`flow_row`、多选对比→`matrix`。不要默认用"节点 + 箭头"硬凑。
- 先盘点已有图，判断"这张图回答的问题还成不成立"；成立就留，不成立就重画而不是叠加。
- 新增图放 `images/`，编号接目录最大值（不要从 01 重来），插在**对应章节**并写"读图"。
- 一篇里有几个独立流程就几张图：总览、时序、边界对照、拓扑，各自分工。
- 生成后必须做 XML + 画布溢出检查，并用 `sips -s format png` 目视复核（`qlmanage` 会裁切宽图）。
- 同步 `images/.readme.md`。

### 5. Glossary and cross-links

- 三列：`术语 | 英文全称 | 解释`；缩写全部展开，非缩写用 `—`。
- 上下文冲突词分别列（如 VLAN `PCP` vs UPnP `PCP`），不要合并成一行。
- 检查 §"与相邻主题的关系"：每个相邻对象都要写**边界**，不能只贴链接。
- 如果正文引用了别的目录的实现细节，改成链接（SSOT 原则）。

### 6. Sync indexes

- 同目录 `.readme.md`：更新一句话摘要（要反映加深后的覆盖范围）、图数。
- 上级 `.readme.md`：篇数不变、图数变化要改。
- 如果新增了图：`images/.readme.md` 补一行。
- 拆篇或改名才动篇数；仅加深不改篇数。

### 7. Verify（回归检查）

按顺序做四件事，缺一不可：

1. **审计**：

   ```bash
   python3 .opencode/skills/knowledge-refactor/scripts/audit_kb.py <dir>
   python3 .opencode/skills/knowledge-refactor/scripts/audit_kb.py <dir> --figure-gaps
   ```

2. **链接回归**：确认原文的链接没丢（文件未提交时先把原文另存一份再比）。

   ```bash
   git show HEAD:"<path>" > /tmp/old.md      # 或用 cp 保存改写前的版本
   grep -o ']([^)]*)' /tmp/old.md | grep -v '^](http' | grep -v '^](#' | sort -u > /tmp/old.links
   grep -o ']([^)]*)' "<path>"    | grep -v '^](http' | grep -v '^](#' | sort -u > /tmp/new.links
   diff /tmp/old.links /tmp/new.links
   ```

   `dead_links` 必须为 0；只在 `old` 里出现的，逐条确认是有意删除。

3. **改动范围**：`git status` 只能出现这一篇 + 它的索引/图；出现无关文件就回退。

4. **图的可视检查**：每张新图渲染成 PNG 看一眼，重点看遮挡、箭头穿字、画布溢出。

### 8. Report

交付时给一张对照表，不要只说"已更新"：

- 打分：改写前 x/10 → 改写后 y/10（列出补上的项）
- 结构：章节数、图数，以及篇幅变化（只报告趋势，不设目标值）
- 修正：二手素材里被推翻的说法（"原说法 → 实际"）
- 待验证：仍然无法核对的点
- 未做：用户没要求、但建议下一步做的（如拆篇、补某张图）

## Deepening techniques（按需取用）

细节与前后对比例子在 `references/enrich-workflow.md`。速查：

| 手法 | 解决什么 | 一句话做法 |
|---|---|---|
| 一句话模型 | 读者记不住 | 用一段 text 图 + 3 条关键认知开场 |
| 分水岭 | 流程分叉讲不清 | 找出"在哪一步分岔"，用图或表固定它 |
| 为什么先行 | 只有结论 | 每个机制先答"不用它会怎样" |
| 边界列 | 表格像字典 | 每列都追问"这列什么时候不成立" |
| 反例 | 结论过强 | 补"有 A 没 B 也成立"的场景 |
| 异常分支表 | 只写成功路径 | 现象 / 根因 / 处理方向 三列 |
| 编号走查 | 读者不会用 | ① 判什么 ② 查什么 ③ 看什么，每步写"答错的后果" |
| 推论 blockquote | 结论散落 | 把"由此得到…"单独拎成块 |
| 状态机 + 定时器 | 动态过程缺失 | 状态表 + 定时器表，没有就明写"没有" |
| 边界声明 | 范围不清 | 开头写"本篇不覆盖 X，去 Y 看" |

## Review gate

10 条硬指标（同 `knowledge-refactor`）+ 三条本技能附加项：

1. **保真**：原文的代码/命令/链接/图引用一条不少（或有明确删除理由）。
2. **深度**：每个 `##` 章节至少有一个解释性判断（"因为…所以…"），不是纯罗列。
3. **无注水**：删掉任意一段，读者会丢失信息；否则那段就是水。

通过线：10 条 ≥9，且 1/4/9/10 必过；三条附加项全过。

## Failure modes to avoid

- **推倒重写**：把原文正确的段落、链接、命令一起换掉，读者失去可对照的版本。
- **为凑结构造章节**：明明没有状态机，硬写一段"状态机概述"。
- **注水式加深**：加背景、加定义、加"随着…的发展"，篇幅涨了信息没涨。
- **图堆开头**：三张图全放 §1，后面的流程章节仍然只有文字。
- **抄基准笔记的章节名**：它那套 `常见坑`/`命令速查` 在本仓库是禁止的。
- **跨篇复制**：把相邻笔记的实现细节抄过来，制造两份正本。
- **改标题不改 TOC**：目录点不动，或锚点全部失效。
- **只跑审计就交付**：审计查不出"读起来像提纲"和"二手断言没核"。
